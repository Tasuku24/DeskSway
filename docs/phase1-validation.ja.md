# DeskSway 第1段階・実機検証結果

検証日：2026-11-03。対象：macOS 27.2（26B123）、Apple Silicon、Xcode 27.2、Swift 6.4.2、論理ディスプレイ1台。

## 次へ進めるか

**この環境の状態検知について、第2段階へ進むための基本検証を通過した。** ソースをコンパイルして動かし、ユーザーが実画面を確認しながら操作した結果と、独立したAX読み取りログを照合した。開くキーの履歴を状態検知の根拠にはしていない。

これはmacOS全バージョンでの互換性、長時間の無故障、入力抑止・キー送信を含む完成品の合格を意味しない。公開AX APIが返す未保証のUI識別子・構造に依存する方式であり、このリスクは公開版にも明示する必要がある。

時刻は各検証プロセス開始からの相対秒。ユーザーの動作時刻や検知遅延そのものではない。画面の観察者はユーザーであり、エージェントが全画面を直接目視したという主張ではない。スクリーンショットやウィンドウタイトルは保存していない。

最初に複数操作をまとめて行ったフルスクリーン確認では、短い開閉が複数記録され、操作との対応を確定できなかった。その結果だけで合格にはせず、静止表示とSpace往復をそれぞれ単独で再実施した。最後の短い再オープンもユーザーへ確認して、意図した操作と対応付けた。

## 判定不能を閉状態と混同しない

第1セッションで以下の一時的な失敗を実際に観測した。

- t=483.973：閉じる遷移中にWindowManagerのAX要素が無効化され、属性読み取りが `-25202`（invalid UI element）となった。`unknown`へ遷移し、t=484.178に次の走査で非アクティブ候補へ回復。約205 msの観測区間。
- t=567.038：対象のWindowManagerプロセスが一時的に列挙されず、`unknown`を出力。t=567.238の次の走査で回復。原因がプロセス再起動だったかどうかまでは未確認。

失敗値を「閉じている」へ変換する処理はない。非アクティブ表示も `inactiveCandidate` と命名し、エラーなく既知の構造が見つからなかった観測値に限る。OS更新で構造が変わった場合と閉状態を完全に区別できるという保証はない。将来の入力処理はunknown、古い検知結果、監視停止時に常に入力を通す必要がある。

## 検知方法、権限、根拠

Swift、AppKit、ApplicationServices、Foundationのみ。200 msを目標にDockとWindowManagerのAXツリーを読む。`mc.display`（または非空のmc）をMission Control、`appexpose.display`をApp Exposéの候補として扱う。役割、識別子、子要素のみを読み、タイトル、文字列入力、画面内容を要求しない。入力監視、イベント抑止、キー送信、AX UI操作はない。

使用した主な公開API：

- [AXIsProcessTrusted](https://developer.apple.com/documentation/applicationservices/1460720-axisprocesstrusted)
- [AXUIElementCopyAttributeValueとエラー](https://developer.apple.com/documentation/applicationservices/1462085-axuielementcopyattributevalue)
- AXUIElementCreateApplication、AXUIElementSetMessagingTimeout

実行ホストのAccessibility信頼判定がtrueで、読み取りに成功した。今回新しい権限付与は行っていない。別のTerminalホストや将来の単独アプリに許可が引き継がれるとは限らない。このプローブにInput MonitoringとScreen Recordingは不要。

`nm -u`でも上記AX APIの参照を確認し、CGS、SkyLight、CGEvent参照はなかった。公開APIの使用と、そのAPIが返すOS内部のUI構造の安定性は区別する。Mission Control専用のApple保証済み状態プロパティを発見したわけではない。

[Hammerspoon issue #3897](https://github.com/Hammerspoon/hammerspoon/issues/3897)と[MissionCloseの実装](https://github.com/beqaabu/MissionClose/blob/main/Sources/MissionControl.swift)で、macOS 27のAXホスト変更を調べた。後者の参照blobは `c1f0ed8da1c17728c55b58190e581e2f30101af3`。別用途の非公開CGS関数は利用していない。今回のプローブは別に実装し、第三者コードやバイナリを同梱していない。参照先の[MITライセンス](https://github.com/beqaabu/MissionClose/blob/main/LICENSE)は確認した。

## 遅延と検知負荷

最後の300秒セッションは1,474走査、平均走査時間3.287 ms、最大77.569 ms（初回を含む）。これは読み取り時間であり、画面変化から検知までの遅延ではない。200 msの目標周期、AX IPC、スケジューリング、アニメーションが別に影響する。エンドツーエンドの正確な遅延は未測定。

AX IPCは対象ごとに150 msのタイムアウトを設定。深さ4・200要素で探索を制限し、上限や読み取り失敗はunknown。複数呼び出しにより1走査が目標周期を超える可能性がある。将来のイベントタップの同期コールバックからAX探索を実行してはいけない。

## BTTと同時条件の予備測定

同じ実操作セッションでプローブとBTTバンドル内の関連プロセスを同時測定。`ps`のRSS・累積CPU時間を約1秒ごとに600回取得した。CPUは連続する両サンプルの観測状態が一致し、PID集合が変わらない区間に限定して、累積CPU時間差÷経過時間で計算。1コア=100%。RSSは取得値の合計をMiBへ変換した。

| 検知状態 | RSSサンプル数 | CPU計算に使えた区間合計 | プローブ平均RSS / CPU | BTT関連合計平均RSS / CPU |
|---|---:|---:|---:|---:|
| 非アクティブ候補 | 480 | 約492.1秒 | 12.81 MiB / 0.44% | 64.34 MiB / 0.46% |
| Mission Control | 108 | 約95.4秒 | 12.66 MiB / 0.79% | 64.93 MiB / 0.65% |
| App Exposé | 12 | 約11.7秒 | 12.93 MiB / 0.51% | 64.91 MiB / 0.34% |

Mission Control区間には実マウスのSpace往復、開閉、静止表示が混在する。純粋な入力負荷だけを隔離したベンチマークではなく、ピークCPUや瞬間的な遅延の証明でもない。状態との対応付けは約1秒の粒度で、短い遷移を完全に分離できない。全操作を含む完成版の測定は別途必要。

BTTは既存の多機能な仕事を継続し、プローブは状態読み取りだけで同等機能ではない。RSSは共有ページの重複、圧縮、スワップの影響を受け、Activity Monitorのメモリやphysical footprintとも同一指標ではない。今回、検知中のプローブCPUはBTTより低くなっていない。**BTTを終了していないため、システム全体のメモリ削減を達成したとは扱わない。**

## 環境の維持

BTTの対象トリガー2個は開始時・終了時とも有効のまま。設定を無効化・削除せず、BTT自体も終了していない。プローブに入力処理がないため二重実行は起きない。Mos、LinearMouse、Karabinerの対象設定ファイルは開始前後でSHA-256が一致。中央ボタン、Fusion除外、スクロール方向・速度・加速・滑らかさは変更していない。

プローブと負荷計測プロセスの終了を確認した。生ログ・個人環境のハッシュ・計測用ファイルは公開対象外のworkに置き、公開用のソースと本報告には個人の絶対パス・署名情報・生ログを入れていない。リモート作成、push、公開は行っていない。プロジェクト名はユーザー指定のDeskSway。公開ライセンスは引き続き未選択。

## 未確認のこと

- 複数ディスプレイ（今回の環境は1論理ディスプレイ）。macOS 27.2以外のOS・Intel Mac。
- 空のSpace、極端に多数のウィンドウなど、今回とは異なるAX構造・規模。
- ホストの権限失効・再付与、ロック・スリープ・復帰、強制再起動からの全回復経路。
- 正確な表示開始・終了から検知までの遅延、長期のCPU・メモリ増加。
- 新アプリによるスクロール抑止、慣性・連続入力の制限、キー送信、その後もMission Controlを維持すること。
- 将来の独立アプリの権限と署名・配布・削除フロー、BTTを終了した場合のシステム全体の削減。

次段階は、確認済みのAX構造を公開APIで読み取る方式をベースとし、unknown・読み取りの遅延・イベント監視停止で入力を遮らない最小実装とする。追加の手動確認では、既存の4修飾キー＋A/SでSpaceを移動して戻り、Mission Controlを維持できたとユーザーが確認した。追加セッションでもt=74.142–89.552に連続してMission Controlを検知した。これは物理キーボードでの成立確認であり、新アプリから生成したキーイベントは未検証。
